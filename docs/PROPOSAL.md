# ofdkit 项目申报书

> 2026 MoonBit 国产基础软件生态开源大赛 · 十一月赛
> 申报人：BenPaoBaMingWangXing　｜　仓库：<https://github.com/BenPaoBaMingWangXing/ofdkit>

## 一、项目名称

**ofdkit — 纯 MoonBit 的 OFD 版式文档生成器与结构校验器**

## 二、一句话说明

让 MoonBit 程序能直接产出符合 GB/T 33190-2016 的 `.ofd` 版式文档，并且能自己证明产出是合法的。

## 三、为什么做这件事

OFD（Open Fixed-layout Document）是国家标准定义的版式文档格式，在电子发票、电子档案、电子证照这些场景里作为 PDF 的国产替代。它的定位不是"再做一个 PDF"，而是把版式文档的数据主权和工具链留在国内标准体系里。

现状是：**阅读器不少，生成器几乎没有**。查重时在 mooncakes 上扫了 3724 个模块，OFD 相关的只有两个——一个阅读器（`colmugx/ofd`），和一个 OFD 发票工具。写入侧是彻底空的。

而写入侧恰恰是业务系统最需要的一环：报表、票据、公文，都要"从数据生成文档"。

MoonBit 生态在这方面同样空白。已有的 PDF 工具（官方 `pdflite`、`Ysh4899/moonpdf`）走的是 PDF 路线；国产版式文档这一块，一个能用的生成器都没有。

## 四、目标用户

1. **需要出报表/票据的 MoonBit 后端服务**——现在只能调外部进程或转 PDF，ofdkit 让这一段留在语言内。
2. **政务/企业系统的国产化迁移**——OFD 是国标格式，很多招标明确要求。
3. **AI 代理**——OFD 的 XML 内容流结构浅，比 PDF 的内容流更适合模型生成和校验。

## 五、功能范围（Scope）

这是验收依据，写清楚做什么、不做什么。

### 本期交付（v0.7.0 已全部完成）

| # | 能力 | 验收方式 |
|---|---|---|
| 1 | OFD 包结构：ZIP 容器、`OFD.xml`、`Document.xml`、每页 `Content.xml`、目录条目 | 解开包逐项检查 |
| 2 | 多页文档，A4 与自定义尺寸 | `verify` 报告页数与 page box |
| 3 | 文本对象：中文/ASCII 混排、字号、颜色 | 渲染截图 + XML 断言 |

| 5 | TrueType 解析与子集化、字体嵌入 | 子集交给 FreeType 渲染，与原字体比对 IoU |
| 6 | 真实字形度量与自动换行 | 与 FreeType 的 `getlength` 逐值对齐 |
| 7 | PNG/JPEG 图片资源 | 从包内提取图片并校验魔数 |
| 8 | 表格（含跨页、表头重复、单元格截断）与水平对齐 | 分页后页数、表头存在性断言 |
| 9 | 文档大纲（书签树） | `Dest` 必须命中真实页面 ID |
| 10 | 结构自校验器（CLI + 库 API） | 16 项检查全过 |
| 11 | 命令行工具：`demo` / `verify` / `info` / `font-info` / `measure` | CI 中实际运行 |

### 明确不做（本期）

- **OFD 读取与渲染**：不解析版面、不栅格化。这是阅读器的事。
- **电子签章（GB/T 38540）**：需要 SM2 椭圆曲线、ASN.1 DER、国密证书链与印模格式，工作量约等于本项目现有全部功能之和；且开发机没有国密证书与验签工具，做了也无法验证。**宁可不做，也不做假签名。**
- **ZIP deflate 压缩**：目前只写 store 模式。引入 deflate 需要新增依赖或自己实现编码器，而字体子集已经压到 18 KB，整包 35 KB，收益不足以抵消依赖风险。这是有意的取舍，写在 README 里。
- **两端对齐、字间距、英文断词回溯**。

## 六、技术路线

```
业务数据
   ↓  Document / Page API（毫米坐标，原点左上）
文档模型
   ↓  序列化
XML（OFD.xml / Document.xml / PublicRes.xml / DocumentRes.xml / Content.xml）
   ↓  ZIP 打包（自研容器，store 模式，时间戳固定）
xxx.ofd
```

配套两层验证：

```
写出的包 → ofdkit verify（独立读取路径：中央目录 → 本地头 → 数据）
         → scripts/verify_ofd.py（Python 标准库，与前一条代码零共享）
```

### 关键实现选择

1. **零第三方依赖**（库包本身）。ZIP 容器、XML 发射器、CRC-32、TrueType 解析与子集化全部自写。理由是构建可复现性——评审要求"整仓构建通过"，少一个依赖就少一个失败点。
2. **写入与校验走不同代码路径**。校验器不复用写入侧函数，避免"用同一个 bug 验证自己"。
3. **坐标统一毫米**，与标准一致，调用方不做单位换算。
4. **字形重编号式子集**。保留 glyph id 的稀疏方案只能到 134 KB；重编号后 18 KB。代价是要重写 `cmap`、`hmtx`、复合字形组件索引三处。

## 七、与现有工作的差异

| | ofdkit | 已有 OFD 阅读器 | PDF 工具链 |
|---|---|---|---|
| 方向 | 生成 | 读取/渲染 | 生成 |
| 语言 | MoonBit | Java/C++ | MoonBit/Rust |
| 自校验 | 有，16 项结构检查 | 无 | 无 |
| 字体子集 | 有，18 KB 量级 | 不需要 | 视实现 |

没有找到可比的 MoonBit 实现。最接近的参考是 Java 的 ofdrw，它是阅读器优先的项目，写入能力是附属。

## 九、验收判据

每条都可机器验证，不依赖主观判断：

1. `moon test` 全部通过（当前 67 个）
2. `moon build --target wasm` 与 `--target js` 均成功
3. `moon run cmd/main -- demo` 能生成 `.ofd`
4. `moon run cmd/main -- verify` 报告 16/16 通过
5. `python3 scripts/verify_ofd.py` 退出码 0，且报告页数、字体、图片、大纲
6. GitHub Actions 全绿（含字体路径与图片路径两条额外分支）
7. 发布的包在 mooncakes 上可 `moon add`

## 十、风险与已知限制

| 风险 | 影响 | 应对 |
|---|---|---|
| 未经真实 OFD 阅读器验证 | 可能存在阅读器兼容问题 | 结构与 ofdrw 产物逐项对齐；后续补阅读器实测（见 DEVLOG 的"已知未验证"） |
| 字体子集丢失 hinting | 小字号边缘与原字体有像素级差异 | 已用 IoU 量化（160px 0.977 / 40px 0.869），轮廓一致 |
| 只支持 BMP 码点 | 生僻字与 emoji 不在子集内 | 文档用到的字符都在 BMP；超 BMP 会在后续加入 format 12 |
| ZIP 不压缩 | 包体积偏大 | 35 KB 量级，可接受；如需可换 deflate |

## 十二、这份项目想证明什么

一个语言的生态缺口，不是靠"再写一个 demo"补上的，而是靠**把某个真实格式的写入侧做对**——包括它的包结构、它的坐标约定、它的字体嵌入、它和既有实现的细微差异。

ofdkit 的每一处修正都来自外部对照：`MaxUnitID` 是 Python 校验脚本查出来的，目录条目和元素顺序是 ofdrw 样例比出来的，`lsb` 是 FreeType 渲染对不上查出来的。这些不是"我觉得对"，是"另一个实现不认"。
