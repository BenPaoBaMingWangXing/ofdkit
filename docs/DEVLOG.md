# ofdkit 开发历程

记录于 2026-11-11。从选题到 v0.7.0，大约十个小时。

## 一、为什么是 OFD

先做的事是查重，不是写代码。

拉取 mooncakes.io 的全部模块列表（`/api/v0/modules?page=0`，3724 条），按关键词做聚类统计。结论很直接：

- 活跃模块 3617 个，其中 2007 个是 9 月之后新增的——赛期这三个月，生态被填了一遍。
- HTTP/1-3、WebSocket、gRPC 这些协议坑，已经被一个团队用 `sans-io` 的方式整套占掉，包描述里的 keywords 直接列着 RFC 编号。
- JSON / YAML / Markdown / Unicode 数据表，同一个人（moonbitstack）在 11 月 7 日到 9 日三天里铺完。
- PDF 读写有官方的 `pdflite`，渲染有 `Yjh4899/moonpdf`。

真正空着的高价值方向只剩几个。OFD 是其中最硬的一个：**国标格式、国产替代核心、写入侧零实现**。

这个判断决定了后面所有工作——不是"我想写个文档库"，是"这个位置空着，而且应该有东西"。

## 二、先把结构做对，再谈功能

第一个版本（v0.1.0）没有碰字体，只做四件事：ZIP 打包、XML 发射、文档模型、校验器。

校验器是刻意早做的。理由很实际：**如果验证方式是"我觉得对"，那这个项目就没有说服力**。所以第一天就写了两层验证：

1. `ofdkit verify`：读自己的产物，但走完全独立的代码路径（中央目录 → 本地头 → 数据），不复用写入侧任何函数。
2. `scripts/verify_ofd.py`：Python 标准库 `zipfile` + `ElementTree`，与 MoonBit 代码零共享。

第一版跑出来 10/10 通过，很漂亮。然后 Python 脚本报了一件事：

```
MaxUnitID 是 4，但对象 ID 到 1012
```

`MaxUnitID` 我直接取了文档计数器，而页面对象 ID 是分段分配的（`page_id * 1000`，为了避开页间冲突）。声明值小于实际值，违反标准。

**这是自己校验自己发现不了的**——校验器如果也用同一个计数器，两边会一起错。

## 三、和 ofdrw 对齐：两个自校验看不到的偏差

v0.1.1 做了件事：下载 ofdrw 的测试样例 `helloworld.ofd`（1651 字节），解开逐个文件比。

比出两处：

**一、ZIP 里必须有目录条目。** 我的包里只有叶子文件（`Doc_0/Document.xml` 等），而真实 OFD 还带着 `Doc_0/`、`Doc_0/Pages/`、`Doc_0/Pages/Page_0/` 三个 0 字节条目。不少阅读器靠这些目录记录遍历包。

**二、`CommonData` 的子元素顺序。** 我把 `MaxUnitID` 放在第一位，ofdrw 的顺序是 `PageArea` → `PublicRes` → `MaxUnitID`。同样是"按标准字面合法"，但和事实实现不一致。

这两处都不是逻辑错误，是**约定差异**。自己的校验器永远发现不了，因为"标准允许"——只有拿别人的产物对比才会暴露。

顺带一提：`Content.xml` 里我原本多加了一层 `<ofd:Area>` 声明页面尺寸，ofdrw 是直接在 `Document.xml` 的 `PageArea` 里声明一次。我改成了后者，更接近事实标准。

## 四、字体：连续踩了三个坑

v0.2.0 做字体嵌入，是整个项目最硬的一段。

一个中文字库 9.7 MB、28,562 个字形。直接塞进文档不现实，必须子集化。

### 坑一：大小端

第一版子集生成出来，FreeType 直接拒绝：`unknown file format`。

原因：我复用了 ZIP 的 `ByteBuf` 写入方法，而那套全是小端——**ZIP 是小端，TrueType 是大端**。sfnt 的表目录、`loca` 的偏移数组，全写反了。

加了 `write_u16_be` / `write_u32_be` 才修好。这个坑代价最大，因为它不报编译错，只在你以为"完成"的时候给你一个 0 有用的错误信息。

### 坑二：校验器一直在"假通过"

修完大小端，验证 `verify` 的输出，发现它说"no embedded fonts"——但包里明明有 `Font_1.ttf`。

查下去：`PublicRes.xml` 里写的是

```xml
<ofd:FontFile>Font_1.ttf</ofd:FontFile>
```

这是**元素文本**，我的校验器却用 `find_all_attr` 按 `attr="..."` 属性去匹配。匹配不到 → 认为"没有字体声明" → 直接 passed。

也就是说，从 v0.1.1 到 v0.2.0，所有关于字体的检查都是空转的。补了 `find_all_tag_inner` 才真正生效。

这件事让我后来加了一条规矩：**每个检查项都要有一个能把它弄失败的负例测试**。现在有"字体文件不是字体"、"大纲指向不存在的页"这些负例。

### 坑三：`lsb` 取错了数组

v0.7.0 做字形重编号（把 134 KB 压到 18 KB），渲染对比发现：宽度全对，但每个汉字都有像素差异。

$$\text{IoU} = 0.73$$

太低，不是抗锯齿差异。查下来：

SimHei 的 `numberOfHMetrics` 是 **855**，`numGlyphs` 是 **28,562**。TrueType 的 `hmtx` 表分两段：前 855 个字形有完整度量（advance + lsb），后面的只在**尾部数组**里存 lsb。

我的代码对超出部分取了"最后一个完整度量的 lsb"，等于所有汉字都用了 `id=854` 那个字形的边距 → 整个字水平偏移。

改成走尾部数组后：

| 字号 | IoU |
|---|---|
| 160 | 0.977 |
| 80 | 0.932 |
| 40 | 0.869 |

剩下的差异是丢掉的 hinting（`cvt`/`fpgm`/`prep`），轮廓一致。字号越小 hinting 影响越大，符合预期。

## 五、度量对表：和 FreeType 逐值一致

v0.3.0 做文本度量。做法很直接：读字体的 `hmtx` advance width，除以 `unitsPerEm` 乘字号。

验证方式不是"看着差不多"，是拿 FreeType 的 `getlength` 逐值比：

| 文本（size=100） | ofdkit | FreeType |
|---|---|---|
| `OFD 文档生成器` | 700 | 700.0 |
| `中文` | 200 | 200.0 |
| `ABCabc123` | 450 | 450.0 |

三个值全等。这条后来写进了 README——因为它证明的不是"我们的度量大概对"，是"我们的度量和事实引擎同一套算法"。

顺带说明一件事：`simhei.ttf` 的 `unitsPerEm` 是 256，不是常见的 1000/2048。如果代码里写死 1000，上面三个值全会错。

## 六、补上"看得见"这一环

到 v0.4.0 时，所有验证都是结构层面的——包能解开、XML 能解析、对象数对。但**版面到底长什么样，没人知道**。

开发机上没有 OFD 阅读器，也不想去装 Java 跑 ofdrw。于是写了个 `scripts/preview_ofd.py`：用 Pillow 把生成的 `.ofd` 读出来，按 `TextObject` 的 `Boundary` 和基线画字、按 `AbbreviatedData` 的 `M`/`L` 画线、按 `ResourceID` 贴图，输出 PNG。

第一次渲染出来，立刻看到两个问题：

1. 表格行高 6.5 mm 时，单元格基线 4.3 mm 视觉上偏上，调到 4.75 mm 才居中。
2. 色块离表格太远，中间一大片空白。

这两个问题，任何结构断言都发现不了。**没有渲染，就没有版面判断**。

README 里那两张预览图就是它产出的。

## 七、关于 AI 工具的使用

这个项目全程有 AI 参与，但分工是明确的：

**AI 适合做的**：把格式规范翻译成代码（ZIP 头、TrueType 表结构、cmap format 4 编码）、写测试、写文档、批量重构。这些工作有明确的正确性判据。

**AI 不适合单独做的**：判断"哪个字段该填什么"。`MaxUnitID` 那次就是——AI 按字面理解填了计数器，但它不知道对象 ID 是分段分配的。这类错误只有靠外部对照才能发现。

所以流程是：**AI 写 → 立即跑 → 用外部工具验 → 不对就查规范**。三个坑（大小端、`FontFile`、`lsb`）全是"跑出来不对"才暴露的，没有一个是"看代码看出来的"。

一个具体的例子：`lsb` 那个 bug，如果只看代码，`index = if old_id < metrics { old_id } else { metrics - 1 }` 读起来完全合理。只有把字形渲染出来、和原字体比 IoU，才会发现 0.73 这个数不对。

## 八、对既有开源工作的借鉴与取舍

**ofdrw（MIT）**：只用来比对产物结构，一行代码没抄。借鉴的是"事实标准长什么样"——目录条目、元素顺序、`Content.xml` 不加 `Area`。它的 1898 个 star 说明这是被广泛使用的实现，那么它的输出就比我的理解更可信。

**FreeType / Pillow**：作为渲染基准。不是"能用就行"，是拿来当裁判——宽度要逐值相等，字形要 IoU 对得上。

**moonbitlang/x**：CLI 的文件读写依赖。库包本身刻意零依赖，因为评审要求"整仓构建通过"，少一个依赖少一个失败点。

**格式规范本身**（ZIP APPNOTE、OpenType spec、GB/T 33190）：`lsb` 的两段式布局、`cmap` 的 format 4 段结构，都是规范里写清楚的。问题从来不是"规范没说"，是"我以为我知道"。

## 九、把限制一条条拆掉

上一版列了四条"没做/没验证"，这一轮全部处理了。

**补上真实阅读器验证。** 之前卡在"开发机没有 JRE"。解决方式很土：下载 OpenJDK 17 的 zip（华为云镜像 177 MB，22 秒），解压到 `_tools/`，再用 `ofdrw-reader` 2.5.1 加它的依赖跑一个 40 行的 `ReadOfd.java`。第一次跑通时读到 `pages=2`、中文正常，才算真的有了"别人能读"的证据。顺带发现：`textObjects=19` 而 `textCodes=90`，说明逐字定位的那种写法它按 `TextCode` 一个个认，没被当成一个坏掉的文本对象。

**把 hinting 找回来。** 之前为了压体积，只复制 `glyf`/`loca`/`hmtx`/`cmap`，把 `cvt `/`fpgm`/`prep` 扔了。代价是小字号下 FreeType 会用自己的对齐策略，IoU 掉到 0.869。加回来只要多写三行"按表复制 + 重算 checksum"，体积从 18,664 涨到 21,536 字节，IoU 变成 1.0000。这笔买卖没有犹豫的余地。

**ZIP 压缩，以及一个只有外部对拍才能抓到的 bug。** DEFLATE 编码器写了 300 行，往返测试一次通过——然后 CPython 的 `zlib` 一句 `invalid distance too far back` 把它否了。两个错：

1. 距离码表漏了 RFC 1951 里"码 2 = 距离 3、码 3 = 距离 4，都不带附加位"这两档，我把它们写成了带 1 位附加位的区间。因为**编码器和解码器用的是同一张错表**，自己解自己永远是对的，CRC 也永远能过。
2. 5 位距离码我按"整数"用了 LSB 优先写入。但距离码在 DEFLATE 里是 Huffman 码（定长 5 位），**所有 Huffman 码都是 MSB 优先**；只有长度/距离的附加位才是整数、才是 LSB 优先。这条区分在规范里写了，但写编码器时脑子里"5 位定长"覆盖了"它是 Huffman 码"。

第二个错很值得记：最小复现是三个字节 `abc` 加一个 `(len=3, dist=3)` 的匹配，zlib 说距离太远——因为 MSB/LSB 读反之后距离码从 2 变成了 8。修完之后整包 51,467 → 32,512 字节，`zipfile.testzip()` 干净返回 `None`。

**表格样式与两端对齐。** 表格加了斑马纹与边框颜色；两端对齐按中文规范把富余量摊到字间，并且规定"两个 ASCII 字符之间不许开口"——否则 `Content.xml` 会被拉成 `C o n t e n t . x m l`。第一版按"空格处分配"写，混合中英的段落一渲染就露馅：所有空隙堆在少数几个空格上，行内像被扯开的口子。看了预览图才改过来。

## 十、仍然存在的边界

- **压缩率不是最优。** 固定 Huffman 不按字节频率自适应，字体这种分布平坦的数据比 zlib `-9` 差 14%。动态 Huffman 要建码长树、传码表，代码量翻倍，换回来的是几 KB。
- **没有版面解析能力。** 生成侧永远不知道自己的输出长什么样，只能靠外部渲染器看。
- **单线程、无流式输出。** 整包在内存里拼装，适合单文档，不适合批量生成十万张票据。
- **没有实现电子签章。** GB/T 38540 需要 SM2、ASN.1 DER、国密证书链，开发机没有验证工具。宁可不做，也不做一个假签名。

## 十一、这十个小时学到什么

**一、验证要独立，不能自己证自己。** 三层验证（自校验、Python 解析、FreeType 渲染）各自独立，才抓得到 `MaxUnitID`、`FontFile`、`lsb` 这三个 bug。

**二、"按标准合法"不够，还要"和事实实现一致"。** 目录条目、元素顺序，标准没说必须怎样，但阅读器认那个样子。

**三、可视化不是锦上添花。** 没有预览渲染器，表格基线偏 0.45 mm 这种问题永远不会被发现。

**四、诚实比漂亮重要。** README 里"现在不能做什么"那一节，比"能做什么"写得更细。评审说"不做过度的能力声明"——那就把没做的、没验证的、刻意取舍的，全部摆出来。

---

最后留一个数字：这个项目从 9.7 MB 的字体里，为一份两页文档保留了 110 个字形、21,536 字节。剩下的 28,452 个字形，是这套文档永远不会用到的部分。

子集化的本质就在这里——**不是压缩，是只带你需要的**。
